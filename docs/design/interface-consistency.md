# Governance interface conventions

Apply these by role across the whole app, including dialogs and expanded proposals.
Current consolidated baseline: 27 September 2026. Saved `/design-locks` and `/design-proposals` variants are historical studies.
The shared rules are in `app/pages/globals.css`; change the named roles, not individual pages.
See [the component catalogue](interface-catalogue.md) and the local `/design-system` page for live examples and the role inventory.

- Rectangular surfaces share `--ui-radius` (6px): buttons, inputs, panels, dialogs, tooltips, menus, badges and resource links. Do not introduce independent corner sizes or pill-shaped controls. `--action-radius` and the ODS rectangular radius tokens alias this value. Rows that touch a card edge use `--ui-radius-inner` (outer radius minus the 1px border); flush interior rows and underline-only fields stay square. Avatars, radio indicators, dots and progress graphics retain their circular geometry.
- Neutral outlines and dividers share `--ui-stroke`, an opaque mix of 16% Interfold Black and white, so the colour stays consistent on white and grey backgrounds. `--rule`, `--rule-soft` and `--rule-strong` are compatibility aliases to that same stroke. Interactive hover outlines use `--ui-stroke-hover` (32% ink). Preserve semantic error/selection/status colours, filled primary actions and visible keyboard-focus outlines.
- Header and footer come from the main website's shared `site-header` package. `SiteFooter`
  supplies the actual website structure and brand typography instead of a local approximation.
  Content uses shared props: Governance links to The Interfold, DAO Constitution, Blog and X,
  with its own copyright and no Updates newsletter. The main site's default content remains.
  The Governance navbar and footer use `--page-ground-shade`; background is the only per-site
  aesthetic difference. All future
  aesthetic changes to either header or footer must be made in the canonical source and synced
  to both sites; preserve the user's approval rule for existing components.
- Header branding, desktop navigation, mobile menu and footer links share the canonical dark-green hover/focus colour. Navigation links retain a visible underline on hover/focus; the current page's underline persists. Use `site-header-menu-link` for mobile destinations; do not restore a bright-mint text hover on pale surfaces. The shared header/footer content frame is 1052px with 16px mobile / 32px desktop gutters, and the page-content tokens alias that frame. Keep both aligned through the canonical package rather than local overrides.
- Voting power and Proposals intro glyphs have no coloured fill. Both match the navbar
  symbol's rendered stroke, using its shared width/height tokens, aspect ratio and
  `INTERFOLD_OUTLINE_RATIO`. Use non-scaling strokes so a larger glyph does not become
  heavier than the mark. Keep the official Interfold symbol artwork unchanged.

- Field labels and table headers: Inter 12px, weight 500, 1.4 line height, sentence case, no tracking. Use `--ui-label-font` and `ui-table-head` for new tables.
- Small content section titles: Inter 16px, weight 600, sentence case (`--ui-section-font`). No decorative dash or duplicate eyebrow.
- Status badges: Inter 12px, weight 600, sentence case. Keep the shared state colors across lists and dialogs.
- Individual lock states use `LockStatusBadge` over `StatusBadge`. Your locks does not repeat the list total in a title badge; state counts remain in saved design studies.
- Destructive actions use `intent="destructive"`: a white secondary surface, dark critical-colour text and a persistent icon. Discard signed ballot uses the trash affordance; ordinary actions retain their existing colours and motion.
- Standard actions use `ActionButton` / `ActionLink`: 52px desktop and 46px mobile, 6px corners, Inter 14px/600. `size="compact"` is explicit: 40px desktop and at least 44px on mobile/touch. Lock FOLD and lock/delegate row actions use compact sizing, with a 196px desktop action column. Vote and Create proposal share a 260px desktop column and the regular size. Never override a component’s dimensions with page-specific button selectors.
- Proposals uses the same external `PanelHeader` as Your locks: title and introduction above the white list panel, with black `ActionLink intent="create"` on the right and eligibility feedback adjacent. Keep the shared divider, heading typography and gap to the panel. Search, filters and proposal rows stay inside the panel. Open voting windows use a green `ActionButton intent="vote"`; View results, View proposal and Close details remain white secondary controls. Public/private vote submission and confirmation use the same green intent; independent mask actions remain black.
- Proposal creation is a functional form: use the shared Inter title/body roles for its compact heading, a reading surface for the written content and a separate surface for voting/submission. Both columns start on the same line; stack below 1024px. Supporting links and DAO actions use the same white surfaces and bending disclosure chevrons as proposal details. Voting method choices share the ballot's radio-row styles. Submit, add-link/action, fee-credit and action-dialog controls use ActionButton. Keep the same mounted draft while changing voting method.
- Ballot options and Voting method show the shared `ActionIcon` check on the selected row, with the existing row highlight. Unselected rows reserve the same trailing space without a hollow-circle marker. Keep the native single-choice inputs, keyboard navigation and focus treatment; vote colours remain at the left, and unavailable masking retains its distinct slashed-circle indicator.
- After a proposal submission attempt, show missing title/summary and incomplete supporting links inline, using the shared critical colour tokens and `FieldError` metadata text. Mark controls with `aria-invalid` and link their explanation with `aria-describedby`; open Supporting links when it contains errors, and focus the first invalid input. Clear feedback as values are corrected. Both voting methods and their submission hooks use `validateProposalDetails`; description, links and DAO actions remain optional. Incomplete metadata must not reach upload, fee approval or proposal creation.
- Proposal resource links, including Read the help guide, use transparent outlined chips on both list expansions and full proposal pages. Hover uses a slight ink tint; do not add a white fill.
- Action affordances use `ActionIcon` (Phosphor regular, shared 16px size and 8px gap) through `ActionButton`, never an independently inserted icon. `ActionLabel` keeps them trailing and hidden below the label at rest, then slides them up on hover or keyboard focus without changing the button width. Apply this to every member of the family: creation, withdrawal, change/select delegate, self-delegation, removal and custom-address selection. Touch and reduced-motion layouts show the icon without animation. Status checks use the same size and stroke but remain visible; disclosure chevrons also stay visible because they communicate state.
- Expand/collapse chevrons use `BendingChevron` from the shared site package, including native details, select fields and `AccordionHeader`. Its two arms bend through a horizontal line with the homepage's 200ms easing; never rotate the whole icon. The canonical source lives in `Interfold-Website/packages/site-header/src` and is synced with `bun run sync:header`.
- Native dropdowns use `NativeSelect`: preserve the native menu and keyboard controls, with a centered chevron inset 16px from the right and reserved space for it. Apply this to filters, directory sorting and mask recipient selection.
- Data columns align left. Lock statuses align right within their column, with the remaining time to the left of the badge; withdrawal actions occupy the final right-aligned column. Delegates retain separate identity, voting power and action columns. Hide redundant Action headers visually, retaining accessible column names.
- Compact mobile rows use a stacked layout: values sit below their related text rather than following a nonexistent desktop column. Keep only labels needed to disambiguate a value.
- Amounts use Inter with tabular lining numerals at every breakpoint, including the main voting-power total, forms, reviews and lists. Units use the secondary text style. Office Code Pro is for addresses and code, not ordinary interface labels. List IDs and ranks use the Inter `RowIdentifier` role.
- Open full page uses the shared `ui-text-action` link role in Inter, with its external-link indicator. Do not let an expanded proposal footer impose a monospace style on interface actions.
- The secret-ballot result summary appears above its tally, using the shared section-title weight and a check for the winning outcome. Emphasise the leading row's label and percentage, with neutral progress tracks. Keep rejected, missing-quorum, tied and empty outcomes explicit; a leading option alone must not replace those outcomes with a success message. The same result component serves expanded proposals and their full pages.
- Highlight the unique leading option's actual progress track: 10px high with a 2px outline in that option's own colour, whether Yes, No or Abstain. The other tracks remain 6px; percentages still determine the filled width. Ties and empty results have no highlighted track, and the separate quorum bar never receives this treatment.
- The lock amount retains an accessible field label but no visible “Amount to lock” eyebrow. The balance below is paired with “Use max”; do not repeat “Available”.
- `AccountOverview` shows Your account, Your voting power at the upper left, a small explanation below, and the owned FOLD balance with its allocation ring at the right. The ring follows the legend height. Unlocked FOLD, Locked FOLD and Bonded appear in the balance list; vesting is included in the applicable balance category, never counted twice or removed from voting-power calculation. The info control explains the actual contributing voting-power amounts.
- Your account, Your locks and Your delegation use separate white cards, with their titles and short introductions above the cards. Personal sections consistently use “Your”. `PanelHeader` shares their 20px/600 title, optional count, supporting text, divider and action alignment with Proposals. Card surfaces share `.ui-panel` / `.power-card`, the common 6px corners and neutral stroke. All page content and navigation use the existing centered 1052px maximum width.
- The Governance homepage uses the same `--page-ground` grey and centered content measure as Proposals and Voting power. Its `.page-content` container shares the Proposals width rule and `--page-content-gutter`; do not restore an independent 1440px frame or mint page background.
- The homepage reuses `PageIntro` without a glyph, including its supporting paragraph measure, muted colour, vertical spacing and entrance motion. Its card titles and learn-more link use the main homepage's underlined, always-visible-arrow pattern through shared `ArrowSlide` / `UnderlinedArrowLink`; arrows roll only on hover or focus and remain still with reduced motion. Remove the step numbers and the decorative rules above the cards. The illustrated cards have an explicitly requested 1px Interfold Black contour and the shared radius, with white copy surfaces. Titles consistently use the 24px Gramercy role; descriptions use the shared 14px Inter body role and related-content spacing. Illustrations retain the original 900:678 framing; the stack conversion uses its sibling `-no-shadow` source edit. The live vector exports and loops are described below. Do not add a dark overlay or gradient. Generated dark artwork and the older `render-home.mjs` exports remain historical studies.
- The homepage's explanation below the entry cards is one compact editorial section: “Private votes. Verifiable results.” in the existing Gramercy heading role, then one Inter body paragraph and the shared underlined “How secret ballots work” link. The explanation starts on the second card's column on desktop and stacks below the title on mobile. Keep the neutral divider and shared spacing; the former long serif paragraph and repeated uppercase feature list are removed.
- Reuse functional type roles: `PanelHeader` titles 20px/600, section titles 16px/600, supporting text 14px/400, metadata 12px/500, `ListTokenAmount` 16px/600 with a 14px unit and 8px gap. Voting totals and proposal/document titles retain their larger semantic roles. Use tabular numerals for every amount.
- Homepage artwork uses fine vector dots from `app/scripts/pointillism/export-dots.mjs`, retaining the original compositions and transparent grey ground. `PointIllustration` now renders inline native SVG, with circular arc paths and SVG animation; do not restore Canvas/WebGL or an animated raster image. Keep the mound still under six-second concentric water waves, sheets rising into the top every 2.4 seconds within a twelve-second cycle, and Govern's ten-second angular current with legible circular openings. Batch by interleaved motion phases, never rectangular spatial tiles: the user spotted the tile seams. Reuse sheet geometry through SVG `use` and preserve transparent overlap with vector masks. Keep the fine dot size; the compact `.points` payload preserves every circle. Retain the static SVG for reduced motion/loading, the shared pause action outside each card link, and paused clocks offscreen/in hidden tabs. Fewer animation elements are an optimization, not a verified mobile frame-rate result. Card destinations and image assignments remain unchanged.
- Do not show an Eligible badge or creation threshold under the voting-power breakdown. Show a quiet “Not eligible to create proposals” notice directly below the total only when a known threshold is not met, with the minimum in its info control. Show the selected method's minimum and the wallet's voting power beside Submit proposal in the shared composer, including both public and secret-ballot entry points; read the configured threshold rather than hardcoding 10K.
- `YourLocks` is always visible in its own card. The header above it contains Your locks, a short introduction and compact Lock FOLD, without a redundant count badge. Rows preserve stable on-chain IDs through `RowIdentifier`; do not replace them with the array index. Centre each ID vertically beside the amount/delegate block, as with delegate-list numbers; keep the amount and its description on one left edge. On stacked mobile rows the ID stays with that block, not the separate status/actions. Lock FOLD opens the existing form. Saved disclosure studies in `/design-locks` are alternatives, not production requirements.
- `/design-power-intros` retains three user-requested section treatments using the real panels and local preview data: short introductions inside all cards, the same headings and copy outside all cards, or only headings inside. It remains development-only. Keep account, locks and delegation consistent within each treatment; keep essential balance/delegation explanations beside their values.
- The user-selected “Intro por cima” (`outside`) is now the default on the main Voting power page as well as the comparison. Separate account → locks and locks → delegation by the same `--power-section-gap`: 64px desktop and 48px mobile, composed from the existing spacing tokens. Preserve the introduction-to-panel spacing and the other study variants.
- Withdrawal operations use `WithdrawalButton`, which wraps the shared action component: Start withdrawal has a clock, Cancel withdrawal a return arrow, and Withdraw FOLD a wallet. Row actions are secondary; confirmation actions are primary. State colours belong to badges, with text labels so meaning does not depend on colour.
- Keep Delegation and its searchable directory together. The current delegate and management actions stay above the open directory. The directory retains its voting-power column and sort control. Its positional numbers use `RowIdentifier`, but do not imply stable IDs. Search/filter/sort and pagination retain their existing data behavior.
- Show “Delegated tokens” under the Delegation heading, with the amount below its label. Sum the token amounts of activated owned locks, including self-delegation; exclude unactivated locks and queued withdrawals. The wallet shown alongside is the single recipient of their voting power. Preserve unknown reads as unknown. Proposal tooltips may still distinguish voting power delegated to others from the snapshot amount used to vote; that separate outgoing-power metric excludes self-delegation. Bonded and vesting remain included in the owner's voting-power total.
- Identify the connected wallet by its compact address followed by the shared “Your wallet” badge. Do not replace its address with “Yourself” or “Myself”. The connected wallet also belongs in the delegate directory, sorted by its current voting power and without duplicating an indexed entry.
- In lock forms, combine wallet roles only where they actually share an identity. Delegation reviews show the current and proposed delegate; lock ownership does not require a duplicate row there.
- Keep Choose / Change delegate beneath the full delegate identity, on the same left edge. The summary shares the directory's two equal columns and gap: Voting delegate and its controls align with the Voting power column below, while Delegated tokens aligns with the directory's left edge. Label/value roles align across the summary; it stacks on mobile. Use the existing compact actions in the shared action-column widths instead of stretching them across the panel. Self-delegation remains available inside the shared chooser; do not repeat a Delegate to myself button in the overview.
- In the shared delegate chooser, the connected wallet occupies its own dark card above the scrollable directory, separated by a 16px gap. Use the same address and “Your wallet” badge as elsewhere, with no duplicate row below. The card and directory rows share a 20px horizontal inset, keeping Select and Delegated on the same right edge. Only the actual current delegate receives the Delegated status; selecting a draft must not imply delegation has already happened.
- In delegate lists and pickers, the current delegation uses the shared green `DelegateStatus` with a visible trailing check, aligned with trailing action icons. Keep the same width, height and right inset as the selection actions. Highlight its row with a pale green background, without a vertical stripe. Draft selections remain distinct from an already confirmed delegation.
- Put Sort at the right of the single directory header. Delegates and Voting power use the same label role. Keep positional numbering in the shared 24px identifier column, identity alongside it, and numeric values aligned within their own column. The directory is always open.
- Both the production lock list and delegate directory are always open. Grouped count/disclosure interactions remain only in saved lock studies.
- Locks and delegate rows use white backgrounds, fine horizontal separators and the same neutral hover/focus treatment. Only the actual current delegate retains its explicit green state. Surfaces reach the interior card edges, with shared content insets.
- The main voting-power explanation uses three horizontal columns on desktop and stacks on narrow screens. Smaller contextual explanations keep the compact tooltip layout.
- Keep confirmation actions last in the dialog, with a consistent 24px bottom inset on desktop. Place errors before those actions; an empty error region must not leave space below a button.
- Remove labels that repeat the enclosing heading, including “Current voting delegate” inside Delegation and “Governance” above Proposals.

- Confirmed public and secret ballots use `BallotSuccess`: a pale-green result panel with a check, “Vote submitted successfully”, and the transaction link when available. The choice list stays hidden until an explicit “Change vote” action while voting remains open. Prepared and submitted ballots use `BallotWalletSummary` to show two equal columns with labels above the wallet identities: “Vote counts for” and “Sending wallet” before submission, then “Vote counts for” and “Sent by” afterward. Explain in the success text that the vote counts for the signer and the sending wallet only pays gas; changing that vote requests the signing wallet before reopening choices. Keep this receipt in memory only. Masks show “Mask submitted” and “Submit another mask”; a mask is not a vote and does not erase its confirmation. Retrying hides the preceding progress, and a failed update must not be presented as successful.

Actions are a separate disclosure for the proposal's on-chain operations; with zero actions, show a compact “Actions 0” stamp instead of an empty accordion or explanatory block. Keep only immediate in-memory confirmations and transaction links, with no mask history or counter stored in the browser.

- Keep routine encryption, submission and gas explanations in the shared ballot header's info control. Confirmation still explains the number of transactions and wallet fees; actual blocking errors remain visible in the panel.

- Secret ballots default to Yes, No, Abstain and Submit a mask as four mutually exclusive selections with one submit button, in both list expansions and full pages. “Submit a mask” keeps its name when a vote is chosen. - Distinguish the mask row with a small gap, a pale surface, a dashed outline and “No voting weight”. Keep its radio control and text aligned with the vote choices. Selection uses a solid outline and the same filled radio marker.

Public voting has no masking capability and states that votes are public. Both embedded and full-page routes render the same adapters. Public vote replacement is available only when the proposal's voting mode and on-chain eligibility allow it.

Current lock delegation does not imply that bonded/vesting power is delegated; explain this beside the snapshot value and keep the snapshot explanation in its info control. Use `BallotEligibilityNotice` for unavailable, loading and disconnected wallets, hiding vote choices and their submit controls. Preserve existing receipts and independent secret-ballot masking for other eligible voters.

## Shared list surface

- Page entrances reuse `ScrollFadeIn` from the main website's shared `site-header/motion` entry point. Keep the same 16px fade-up, 600ms easing and 140ms document-order sequence for intros, section headings, panels and footer content. Preserve existing HTML and layout through its `as` prop. Tall lists use `amount="some"`; filters and live balances do not restart an entrance. Reduced motion and keyboard focus show content immediately, and unmounting cancels queued work. This is separate from existing dialog/disclosure transitions.

- Locks, the delegate directory and delegate picker use white rows, a thin divider and the same `--surface-muted` hover/focus-within. The current delegate remains an explicit green state.
- Hover and separators reach the card’s interior edges; content retains 32px desktop / 20px mobile insets. No zebra backgrounds or inset hover rectangles.
- Lock amounts and their delegate metadata stack without an extra row gap; align the delegate label and wallet identity on the same line when space allows. - Mobile locks keep the ID beside the amount and delegation, status on the right on the next line, and a full-width action below. Delegate rows keep identity and power grouped, with the action below when space requires it.
- `StatusBadge` shares dimensions (24px high), type, padding and shape; `LockStatusBadge` supplies its domain icon/label/colour. `DelegateStatus` is a read-only indicator sized to the compact action column.
- `SearchField` owns the search icon, clear button, accessible label, border, focus and responsive height on both pages. Filters remain native `NativeSelect` controls.
